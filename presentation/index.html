Overview

Building blocks, layer by layer

Each layer only calls the one below it. Files and the config carry state between them, and guardrails apply to all of them.

Entry points

  • /trello-to-commit in an interactive session
  • scripts/run-pipeline.mjs: headless claude -p

Orchestrator

  • trello-to-commit runs the stages in order
  • Reads each stage's result block and stops at the first failure

Stage skills

  • trello-intake
  • ship-branch (spec / code)
  • implement-spec
  • trello-report

Subagents

  • trello-analyst (analyst)
  • implementer (developer)
  • verifier (QA)

Shared state

  • .claude/pipeline.json: config
  • specs/_template.md, spec.md
  • .pipeline/<card>/*.md: reports

External systems & guardrails

  • Trello MCP, git, GitHub (gh api), CI
  • settings.json, guard-git, typecheck

Stage skills → subagents

Two skills delegate to subagents

Subagents never call each other. The skill in the main session runs them and passes data between them.

trello-intake → trello-analyst

  • Runs the analyst on the card URL and handles READY, NEEDS_CLARIFICATION or EXISTS
  • Validates the spec against _template.md; on violations it reruns the analyst once
  • Promotes Status: Draft → Approved, which the analyst cannot do

implement-spec → implementer + verifier

  • Never edits code itself. Every change goes through implementer, every verdict through verifier
  • Saves each verdict to verify-<n>.md, the final one to verify.md
  • Retry count comes from maxRetries in pipeline.json

The implement → verify loop

implementercode + tests from spec
attempt n
STATUS: DONE →
verifierbuild · tests · smoke · diff review
PASS →
verify.md→ ship-branch code

FAIL and n ≤ maxRetries

The full verifier report (AC table + FIX) goes back to implementer: "fix only the FAIL items".

FAIL after all retries, or implementer BLOCKED

implement-spec comments on the card, moves it to Blocked and leaves the working tree for inspection.

Cross-cutting dependencies

Guardrails wrap every component

These are not called by any component. Claude Code applies them to every tool call, in the main session and in subagents, whether the run is interactive or headless.

.claude/settings.json: allow / deny

  • Headless runs have no prompts, so a command not on the allow list is rejected
  • Every new command a skill or agent uses must be added here
  • Denies force-push, push to main, reset --hard, board edits, .env

guard-git.mjs: PreToolUse on Bash

  • Reads git.baseBranch from pipeline.json
  • Blocks commits/pushes to the base branch, force-push, --all/--mirror/--delete, non-GET gh api
  • Mainly protects ship-branch; parses chained commands too

typecheck.mjs: PostToolUse on Edit/Write

  • Runs tsc --noEmit after each .ts edit
  • Gives implementer type errors right away, before verifier runs, which saves retries

GitHub Actions CI

  • Runs outside the agent: npm ci, build and tests on feature/**
  • Only depends on the pushed branch, so it doesn't rely on the verifier's verdict

Summary

Key takeaways

Calls go in one direction

entry → orchestrator → stage skill → subagent. Nothing calls back up, and subagents never call each other.

Data goes through files

The spec and the .pipeline/<card>/ reports are the interfaces between stages. Their formats are contracts.

One config

pipeline.json is read by nearly every component, including a hook. settings.json is the one place that duplicates part of it.

Guardrails apply everywhere

Permissions and hooks wrap all components, so safety doesn't depend on any one prompt being followed.
